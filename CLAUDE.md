# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant React app for AUK Marine & Mining (maritime/mining training & logistics): a 3-year marketing/sales planning model (service revenue, marketing funnels, budget allocation, CRM/MIS activity tracking, AI-generated campaign/business-plan content) plus an AI-driven prospecting pipeline (web-search research → HubSpot CRM sync → AI-drafted outreach with human review → Resend-based sending → cron-drafted follow-ups, also human-reviewed). Each client organization's data is isolated by Clerk Organization; the rest of the app is one client-side React bundle plus a handful of Vercel serverless functions.

## Commands

- `npm run dev` — start Vite dev server (frontend only — see "Local development" below, this alone won't serve `/api/*`)
- `vercel dev` — full local stack (frontend + API functions against real Clerk/HubSpot/Anthropic services, and an isolated Neon branch for the database — see "Local development" below); the practical way to test anything auth- or persistence-related
- `npm run build` — production build (outputs to `dist/`)
- `npm run preview` — preview the production build locally
- No test suite, linter, or type checker is configured.

## Local development

- **Development's `DATABASE_URL` and `DATABASE_URL_TENANT_APP` both point at an isolated Neon branch (`rls-test`, host `ep-royal-heart-b2vdyqmm...`), not production** (fixed 2026-08-26, closing a long-standing gap where Development had silently shared Production's `DATABASE_URL` since the Neon integration was first set up). This matters because commit `122565f` rewrote the 5 tenant-scoped handlers (`tenant-data`, `prospects`, `outreach`, `send-outreach`, `hubspot-sync`) to use `withTenant()`/`DATABASE_URL_TENANT_APP` exclusively, with no fallback to the owner `DATABASE_URL` — if the two vars ever point at *different* databases (e.g. one at production, one at a branch), local dev silently split-brains: some handlers hit one DB, others (`cron-follow-up.js`, `scripts/*.mjs`, anything still on the owner connection) hit the other. Keep both vars pointed at the same database, always — when repointing one, repoint the other identically. The `rls-test` branch has real seed data (tenants, prospects, etc.) from whenever it was branched, so local testing isn't working against an empty DB.
- `vercel dev` needs env vars pulled locally first: `vercel env pull .env.local --environment=development`. When adding a *new* env var in Vercel, scope it to Production, Preview, **and** Development in one pass — a var scoped only to Production/Preview silently won't reach `vercel dev`, which has repeatedly been the cause of local 401s that had nothing to do with application code.
  - **`.env.local` itself is not what `vercel dev` reads for the function runtime.** Per Vercel's own docs, `vercel dev`/`vercel build` source env from a registered-project-variable snapshot under `.vercel/` (populated by `vercel pull`, a different command from `vercel env pull`) — a line added straight to `.env.local` that was never registered with the Vercel project (never went through `vercel env add` or the dashboard) will read as `undefined` inside a serverless function, even though `.env.local` looks correct and the dev server was freshly restarted after the edit. Confirmed by direct diagnostic logging: `DRAFT_DRY_RUN=true` sat correctly in `.env.local` for hours before a clean `vercel dev` restart, and `process.env.DRAFT_DRY_RUN` still came back `undefined` in `api/_lib/anthropic-client.js`. Fix for genuinely local-only vars (like `DRAFT_DRY_RUN`/`DRY_RUN_RECIPIENT`) that must never be registered with Vercel at all: shell-export them before launching `vercel dev` instead — e.g. `DRAFT_DRY_RUN=true DRY_RUN_RECIPIENT=... vercel dev` — plain OS child-process env inheritance reaches the function fine, no Vercel project registration involved. Deliberately don't "fix" this by registering them as real Development-scoped Vercel vars: `vercel env add [name]` with no environment argument defaults to **all** environments, which is exactly the kind of one-command mistake that could put a "return fake content" flag into Production.
- `vercel dev` is prone to intermittent crashes on Windows (`ECONNRESET` / libuv `UV_HANDLE_CLOSING` assertion failures, unrelated to this app's code) that kill the whole dev server. If localhost stops responding, check whether the `vercel dev`/`vite` processes are still alive and restart if not — this has recurred across sessions and isn't a regression to chase. One recurring signature: a libuv assertion in `src\win\async.c` (line ~94) that kills the server some time after handling requests, not immediately on startup — if a `vercel dev` session that was working starts refusing connections mid-session, this is more likely than a code regression; just relaunch.
- `vercel.json` intentionally has **no** SPA catch-all rewrite — an earlier `/(.*) → /index.html` rule swallowed Vite's own dev-server asset requests under `vercel dev`. Nothing in this app needs it since there's no client-side router.

## Credential handling

- **Never echo a secret value in full** in chat/output — not `CRON_SECRET`, not API keys (`ANTHROPIC_API_KEY`, `RESEND_API_KEY`, `HUBSPOT_ACCESS_TOKEN`, Clerk keys), not `DATABASE_URL`/connection strings. Reference by variable name, or by first 8 characters if disambiguating between two values (e.g. confirming a rotation actually changed something) is genuinely necessary.
- **Never write a credential to disk** (e.g. `vercel env pull --environment=production` to a new file) without asking first, even transiently and even if deleted immediately after. Reading `.env.local` — which the user already created themselves via their own `vercel env pull` — is fine; pulling a *different* scope's values to a *new* file is a separate action that needs a go-ahead first.
- Both of these came up as real mistakes during the Checkpoint 4 build, not hypothetical concerns.

## Architecture

- **`src/App.jsx`** (~2900 lines) is effectively the entire application. There is no router and no component-file split — every tab/section is a function component defined in this one file, rendered conditionally by the `tab` state in `AppShell` (search `const NAV = [...]` around line 818 for the tab list, and the `tab === "..."` block right after it for what renders each one). When asked to work on a specific tab (e.g. "Funnel Plan", "Prospecting"), grep this file for the matching function name (e.g. `function Funnel(`, `function Prospecting(`) rather than trying to read the whole file.
- **Auth & tenancy** (Clerk Organizations): `main.jsx` wraps the app in `<ClerkProvider>` using `VITE_CLERK_PUBLISHABLE_KEY`. `App.jsx`'s `AuthGate` (~line 592) gates on sign-in state and an active organization — signed out shows Clerk's embedded `<SignIn/>`; signed in with no org shows a "contact your admin" message (org membership is granted manually via the Clerk dashboard, there's no self-serve flow). Once there's an active org, `TenantDataGate` (~line 553) fetches that org's saved data from Neon before mounting `AppShell` (~line 619), which holds all the app's `useState` — `AppShell` never touches `localStorage`.
  - This Clerk instance issues **v2 session tokens**, which carry org info as a compact `o: {id, rol, slg}` claim rather than the flat `org_id` field older Clerk docs describe — see `api/_lib/auth.js`'s `resolveOrgId`, the single place this is handled.
- **Persistence** (Neon Postgres, tables `tenants` / `tenant_data` / `tenant_activity`): `AppShell`'s state is seeded once from the `savedData` prop (fetched by `TenantDataGate`), then auto-saves via `persistNow` → `POST /api/tenant-data` on a 1200ms debounce, same as the old localStorage version. The `beforeunload`/`pagehide` flush uses `navigator.sendBeacon` instead of `fetch` (unreliable mid-unload) — since `sendBeacon` can't set an `Authorization` header, the Clerk token rides along in the beacon's JSON body instead, kept fresh via a periodically-refreshed `tokenRef`. `buildSaveData()` is still the single source of truth for what gets persisted — add any new piece of `AppShell` state to both its `useState` seed and `buildSaveData()`'s returned object.
  - `api/tenant-data.js` verifies the caller's Clerk token server-side and derives the tenant (org) id from it — the client never asserts which org it's reading/writing. `POST /api/tenant-data` merges into the existing row rather than replacing it — see the Business Plan / Portfolio section below for the fuller story on why.
  - `api/login.js` (old shared-password auth) and `api/generate.js`'s original localStorage-based flow are obsolete/unused but were deliberately left in place for rollback; don't build on `api/login.js`.
  - One-off admin/migration scripts live in `scripts/` (e.g. `scripts/backfill-auk-category-b.mjs`) — plain Node ESM files using `@neondatabase/serverless` directly against `DATABASE_URL` from `.env.local`, run manually (`node scripts/...`), not part of the app or any build step. Follow that script's pattern for future one-off DB work: default to a read-only `--list`/dry-run mode, require an explicit `--write` (and ideally a specific `--tenant-id`, not "the only row") to actually write, and only ever fill/overwrite the specific keys the migration is about — never a blind full-row replace. Critically, **run these only with zero open browser tabs/sessions for the affected tenant, anywhere** — see the merge-fix known gap below for why.
- **Business Plan / Portfolio content is tenant-scoped** (`BizPlan` ~line 1849, `Portfolio` ~line 1025, `MIS` ~line 2368): SWOT, Strategic Pillars, Focus/Avoid, Business Models (per service id), the Ansoff matrix, Partners, Vision, GP-per-unit, and `Portfolio`'s per-service `note`/`segsCust`/`segsCargo`/`landingPrice` (`portfolioMeta`) are all `AppShell` state following the same `_saved.x || X_SEED` pattern as everything else, each with a generic/fictional `*_SEED` default for a brand-new tenant with no saved data. **Until 2026-08-23 these were read straight from hardcoded module-level consts with zero per-tenant override at all** — every signed-in user of every organization saw AUK's real SWOT, real confidential partnership/shareholding structure (real stakes, real named entities), and real business-model notes, not just brand-new tenants. `Portfolio`'s `groups`/`items` (course codes, consulting offering names) were already tenant-scoped via `portfolioItems` before this fix — only the fields now in `portfolioMeta` were the actual gap. The module-level `*_SEED` consts now hold only generic placeholder content, reviewed field-by-field for structural echoes of the real data (not just literal text matches) — same ordering, same pairing, same counts, same numeric ranges all deliberately varied, not just reworded.
  - **Company/tenant identity in AI-generated content is real, not hardcoded** — same fix, same date. `Campaign`'s social-post prompt, `Prospecting`'s outreach-drafting and research prompts, and `BizPlan`'s AI Trend Radar prompt all use the signed-in tenant's real org name (Clerk's `useOrganization()`, threaded down as a `companyName` prop) instead of a hardcoded "AUK Marine & Mining (auk-maritime.com)". This wasn't just a confidentiality issue — it was a functional bug: every non-AUK tenant's AI-drafted content would have falsely claimed to represent AUK to their own real prospects/clients. A related, AUK-specific "AI-driven marketing consulting" cross-sell pitch that used to be forced into every outreach email regardless of which tenant or service was being pitched was removed entirely (not genericized — it assumed every tenant sells that exact service, which is business logic, not a naming problem). `is_peer` prospects (a candidate that's a peer/competitor in the very service being prospected, not a customer) have drafting disabled rather than reintroducing that assumption; re-enable properly once the cross-sell becomes real tenant-configurable data.
  - **`POST /api/tenant-data` merges into the existing row instead of replacing it** (`tenant_data.data || payload`, a Postgres jsonb shallow top-level merge in the `on conflict do update`) — added alongside the fix above. This protects against a client running an older bundle that predates some newer top-level field: its `payload` simply won't mention that key, so the merge leaves the existing value alone instead of a full replace wiping it out.
  - **Known gap: the merge above does NOT protect against a stale-but-current-code client re-saving a value it already committed to before an out-of-band write.** A tab that mounted (and so already fixed some field's value in its React state) *before* a direct-DB migration/backfill runs will still legitimately include that now-stale value in its next autosave payload — the merge lets it win, since the key genuinely is present, just outdated. This is exactly what happened live during the 2026-08-23 Category B fix: a backfill correctly wrote AUK's real `partners`/`swot`/`bizModels`/etc. content, and an already-open tab's routine post-mount autosave silently overwrote those same fields with the generic fallback values it had already computed before the backfill ran — twice, actually, including once more via production (which didn't have the field-wiring or the merge fix yet) after the first recovery attempt, before both the code fix and a second recovery write were done with zero tabs open anywhere. The real fix is optimistic concurrency (client tracks the version/timestamp it last read; server rejects or reconciles a write against a row that's changed since) or client-side dirty-tracking (only ever send fields the user actually touched, not a full snapshot) — neither is built yet. **Until then: any direct-DB write/migration must be done with zero open tabs/sessions for the affected tenant, anywhere, on any URL (including production)** — that operational rule, not the merge alone, is what actually prevents a repeat.
- **Prospecting pipeline** (`Prospecting` component, ~line 2681; tables `prospect_runs` / `prospects`, tenant-scoped): pick one of the tenant's own services, Claude does a capped (`max_uses: 5`) web-search run via the same `/api/generate` proxy pattern as `BizPlan`'s AI Trend Radar, and results are persisted via `api/prospects.js` (GET lists saved runs+candidates, POST saves a freshly-generated run). **Contact info is never invented** — a candidate is only `verified` if a real, verifiable contact/email came back from search; enforced both in the prompt and again server-side (`api/prospects.js` recomputes `verified` from `!!contact_email`, doesn't trust the client's flag). Each run stores a rough cost estimate (tokens + search count, from `/api/generate`'s `usage` block) in its `criteria` jsonb column.
  - **HubSpot sync is per-tenant, not a single shared portal** (`CLAUDE-CODE-BRIEF-hubspot-per-tenant.md`, built 2026-08-27, verified against two real separate HubSpot portals). `tenants.hubspot_token` (nullable `text`, added via `scripts/add-hubspot-token-column.sql`) holds each tenant's own HubSpot private-app token, managed through a settings card in the Prospecting tab (`api/hubspot-token.js` — GET returns only a last-4-chars mask, never the raw value; POST saves it). `api/hubspot-sync.js` pushes prospects with `status = 'new'` into HubSpot as Company (+ Contact, only when an email exists) records, find-or-create on both (idempotent — safe to re-run), then marks them `queued` with the resulting HubSpot record id — it looks up the signed-in tenant's own `hubspot_token` from `tenants` via `withTenant()` first and returns a friendly 400 ("Connect your HubSpot account first") if unset, with **no fallback to the `HUBSPOT_ACCESS_TOKEN` env var**. That env var still exists and is used only as the source value for AUK's own backfilled row (`scripts/backfill-auk-hubspot-token.mjs`) — treat it as legacy/bootstrap-only, not something `hubspot-sync.js` reads directly anymore. A `pat-...` token (works the same regardless of whether it was generated via HubSpot's classic Private Apps UI or the newer Service Keys UI) authenticates against exactly one HubSpot portal — there is no test/live token split like Clerk. `tenants` already had RLS scoped by `id` from the earlier Task 3.2 work, so `hubspot_token` is automatically covered by the same policy/grant, no new RLS work needed for this column.
  - Outreach drafting (`api/outreach.js`, table `outreach_emails`) is AI-generated per prospect (same `/api/generate` proxy pattern), lands in a review queue, and requires a human `approve` click (`approved_by`) before `api/send-outreach.js` will touch it — there is no auto-send path anywhere in this pipeline, by design.
  - `api/send-outreach.js` sends an approved draft via Resend, records `sent_at`, marks the prospect `sent`. No verified sending domain yet, so it sends from Resend's shared `onboarding@resend.dev`, which Resend restricts to delivering only to the account's own verified email until a domain is added. Resend's free tier caps at 100 emails/day; hitting that cap surfaces as a distinct, actionable 429 (`quotaExceeded: true`) rather than a generic failure — the draft is left unsent, not silently dropped or retried.
  - `api/cron-follow-up.js` (Vercel Cron, `vercel.json` → daily at 06:00 UTC) finds `outreach_emails` sent 5+ days ago with no follow-up drafted yet, and drafts one per prospect — lands in the same human review queue, never auto-sends. Since it's server-side with no browser involved, it calls the Anthropic API directly (same key, same call shape as `api/generate.js`) rather than through that proxy. Guarded by `CRON_SECRET` (Vercel auto-attaches `Authorization: Bearer <CRON_SECRET>` on scheduled invocations when that env var is set) so the publicly-reachable cron URL can't be triggered by an outsider.
  - **Known gap: no reply detection.** There's no inbound-email webhook, so `cron-follow-up.js` cannot actually tell whether a prospect replied — "no reply after 5 days" is really "no follow-up drafted yet, 5+ days after send," regardless of replies. Every such draft is identifiable via `follow_up_of` being non-null, and the UI (`src/App.jsx`, review queue render block) shows a warning on those specifically ("Auto-drafted after 5 days... confirm there's been no reply before approving") so the gap is visible at review time rather than hidden. Real fix is a Resend inbound-email webhook (or, as a lighter interim step, a manual "mark as replied" toggle) — not yet built.
  - **Known gap: `api/cron-follow-up.js` still hardcodes AUK's identity.** The browser-side prompts (`Campaign`'s social-post generator, `Prospecting`'s outreach-drafting prompt in `src/App.jsx`) were fixed to use the real tenant's org name (via Clerk's `useOrganization()`, threaded down as `companyName`) and had a hardcoded "AI-driven marketing consulting" cross-sell pitch removed entirely (it assumed every tenant sells that service — not a naming issue, wrong business logic; `is_peer` prospects now have drafting disabled instead, since they had no valid pitch to begin with once the cross-sell was removed). `cron-follow-up.js` needs the **same three changes** (real tenant name instead of "AUK Marine & Mining... auk-maritime.com", cross-sell removed, peer-drafting disabled) but hasn't been touched yet — it's a separate file with its own copy of this logic. Not yet exploitable in practice (no second tenant has been onboarded — access is fully gated by manual Clerk org creation), but must be fixed before onboarding a second tenant that uses the Prospecting pipeline. The real tenant name is available server-side via the `tenants.name` column (see `api/tenant-data.js`'s `orgName` piggyback, added alongside this fix) — `select name from tenants where id = tenant_id`, same pattern as `api/send-outreach.js`'s `fromAddress()`. Related, minor, and deliberately deferred alongside it (2026-08-26): a sent outreach draft's signature read "auk-maritime.com" (missing the `www.` prefix Ashwani prefers) — but that string wasn't a fixed template anywhere; the browser-side `draftOutreach` prompt (`src/App.jsx`) never mentions a domain at all, so the model supplied it itself as free text. There's no tenant "website" field in the data model to thread in instead, and hardcoding any specific domain into that prompt would reintroduce the same anti-pattern this fix already removed. Proper fix is a real per-tenant website field, not a string edit — do it as part of (or right after) the tenant-identity fix above, not as a standalone cosmetic patch.
  - **Known gap: app branding is not tenant-scoped.** The logo, "AUK Marine & Mining" title/alt-text on the sign-in screen and the app's own top bar/sidebar (`src/App.jsx`, `AuthScreen`/`AppShell` render) are hardcoded — every tenant signing into this app sees AUK's branding as the product's own identity, not their own. This is a full white-labeling effort, out of scope for a seed-data or prompt-identity fix — see the untracked `CLAUDE-CODE-BRIEF-multitenant.md` in the repo root, which appears to already scope this separately.
  - `tenant_usage` (table, one row per tenant per month) counts `research_runs`, `ai_drafts`, `emails_sent` — incremented at each corresponding action in `api/prospects.js`, `api/outreach.js`, and `api/send-outreach.js` respectively. Counting only, no enforcement/limits yet — that's billing work, deliberately out of scope for this pass. Usage is NOT incremented for anything created while `DRAFT_DRY_RUN` is on (see below).
  - **`outreach_emails.dry_run`**: while `DRAFT_DRY_RUN=true`, every row `api/outreach.js` and `api/cron-follow-up.js` insert is tagged `dry_run = true` (its content is `/api/generate`'s canned placeholder, not a real draft) — the UI shows a red "DRY RUN — not real" badge on these in the review queue so one can't be mistaken for real and approved by accident. `api/send-outreach.js` additionally hard-blocks sending to a real prospect while dry-run is on: it reads `DRY_RUN_RECIPIENT` and forcibly overrides the send target to that address (subject prefixed `[DRY RUN — real recipient was ...]`) rather than `contact_email`; if `DRY_RUN_RECIPIENT` isn't set, it refuses to send at all rather than falling back to the real prospect. `api/cron-follow-up.js`'s eligibility query excludes `dry_run = true` rows so fake sends never trigger a real follow-up draft. `resolveRecipient()` in `api/send-outreach.js` is exported specifically so this invariant (never the real address while dry-run is on) can be tested directly, without a network call.
- **Shared server-side auth helper**: `api/_lib/auth.js` exports `resolveOrgId(req)`, used by both `api/tenant-data.js` and `api/prospects.js`/`api/hubspot-sync.js`. Files/folders under `api/` prefixed with `_` are skipped by Vercel's routing, so this isn't itself an endpoint. Includes a 10s `clockSkewInMs` tolerance in its `verifyToken` call — request latency was occasionally pushing verification past a session token's ~60s expiry.
- **Derived business-model data** (`calc`, `funnelCalc`, `mktCost`) is computed with `useMemo`/plain expressions in `AppShell` from the raw service/budget state and passed down; tab components generally don't recompute business logic themselves.
- **AI features** generally: the browser calls `/api/generate`, a Vercel function that proxies to the Anthropic Messages API using the `ANTHROPIC_API_KEY` env var, so the key never reaches the client. It's a stateless pass-through — no tenant/auth logic in it. Any new **browser-triggered** AI feature should go through this same proxy pattern rather than calling Anthropic directly from the browser, and should cap `web_search`'s `max_uses` rather than leaving it uncapped (an uncapped run once cost $2+ in a single click). The one exception is `api/cron-follow-up.js`, which runs server-side with no browser involved and calls Anthropic directly — the proxy's reason to exist (keep the key off the client) doesn't apply there.
  - Both `api/generate.js` and `api/cron-follow-up.js` call the actual Anthropic API through a shared `api/_lib/anthropic-client.js` (`callClaude(messages, opts)`, returns `{ status, data }`). It also carries a `DRAFT_DRY_RUN` escape hatch — set `DRAFT_DRY_RUN=true` in `.env.local` **only** (never in Vercel's Production/Preview scopes) to return a canned placeholder response instead of calling Anthropic, useful for iterating on drafting/cron logic locally without a valid key or real API spend.
- **Styling**: a single template-literal CSS string (`const CSS`, near the top of `App.jsx`) injected via a `<style>` tag — no CSS modules, no Tailwind, no styled-components. Color tokens are CSS custom properties (`--navy-900`, `--brass`, `--teal`, etc.) reused across inline styles throughout the file.
- **`ErrorBoundary`** wraps the active tab's content (keyed by `tab`), so a crash in one tab doesn't take down the whole app — it resets when the user switches tabs.
- **Charts** use `recharts`; icons use `lucide-react`.
- **Deployment**: Vercel, project `auk-marketing-model` under the `auk-inspections` team. Env vars that matter: `DATABASE_URL` (Neon), `CLERK_SECRET_KEY`/`CLERK_PUBLISHABLE_KEY`/`VITE_CLERK_PUBLISHABLE_KEY`, `ANTHROPIC_API_KEY`, `HUBSPOT_ACCESS_TOKEN`, `RESEND_API_KEY`, `CRON_SECRET` — all should be scoped to Production, Preview, and Development (see "Local development" above for why Development matters). `APP_USERNAME`/`APP_PASSWORD` still exist for the retired `api/login.js` but aren't used by the live app. `DRAFT_DRY_RUN` and `DRY_RUN_RECIPIENT` are the opposite — local-testing-only, must NEVER be set in Vercel's Production or Preview scopes (`.env.local` only).
